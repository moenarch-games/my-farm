- **How to use this Decision Atlas**
  - This project owns one canonical Markdown source: `docs/decisions/atlas.md`. It records approved product decisions. GitHub issues contain the detailed work/acceptance contracts; the shared Decision Atlas viewer, when built, is read-only.
  - Every explicit dotted number is a stable decision or branch ID, for example `3.5.2`. Cross-references refer to these IDs, **not** Markdown's automatic numbering.
  - **Append-only rule:** add the next unused child number under the relevant parent; never renumber, reorder, delete or reuse an existing ID. Superseding an approved choice requires a new ID referring to the old one; the original remains visible. Concurrent writers must reconcile sibling IDs before merging.
  - Older `my-farm/...` path IDs are preserved as legacy aliases on the imported decisions. Do not reinterpret or recycle those older identifiers; use dotted IDs for future references.
  - `[agreed; implementation unverified]` means the owner has selected a design, not that the corresponding gameplay works. Add precise source/test references only after checking them. Existing architectural [ADRs](https://github.com/moritzbrantner/my-farm/tree/main/docs/adr) remain valid and distinct.

- **3** Production goals and scheduling
  - **3.1** Goal admission and resources

    - **3.1.2** [agreed; implementation unverified] **A** — Every real starting input, Resident/Tool/facility slot, producing step and Silo/Barn capacity must be reservable for the entire chain; otherwise reject completely with explanation and never auto-buy.   - **3.2** Commitment scheduling and cancellation
    - **3.2.1** [agreed; implementation unverified] **A** — Prefer the earliest feasible completion for the entire goal, using legitimate parallelism, bounded deterministic planning, and no preemption of accepted commitments.     - **3.2.2** [agreed; implementation unverified] **B** — On goal cancellation finish currently active steps and required cleanup, stop future steps, keep completed goods and safely release only unused future reservations.   - **3.4** Player feedback

Tags: `history`, `hud`. Legacy alias: `my-farm/production/feedback/recent-completed-goals`.
  - **3.5** Goal-completion XP
    - **3.5.1** [agreed; implementation unverified] **B** — Completing a player-authored finite `Produce N new` goal grants **additional XP** beyond existing farming/production XP, exactly once on the final successful goal-attributed Barn deposit (N/N). Incomplete or cancelled goals earn no completion XP. The XP is awarded by the authoritative Farm progression model and shown in the compact completion notification/history; **selected B:** completion XP scales with genuine goal-attributed production effort. Equivalent work (one 10-Bread goal versus ten 1-Bread goals) should earn approximately the same aggregate bonus, without a flat per-goal jackpot. The effort metric is now **B: standard catalog production difficulty based on canonical product/recipe requirements**, not actual Resident time, travel, waiting or inefficient work. The standard value's manual/derived authoring method and XP conversion rate remain open; no diminishing-repeat policy is approved. [#200](https://github.com/moritzbrantner/my-farm/issues/200), [#133](https://github.com/moritzbrantner/my-farm/issues/133), [#135](https://github.com/moritzbrantner/my-farm/issues/135). Tags: `progression`, `xp`, `reward`. Legacy alias: `my-farm/production/rewards/goal-completion-bonus-xp`.
    - **3.5.2** [agreed; implementation unverified] **B** — Bonus XP uses the product/recipe's **standard catalog-defined production effort** grounded in its canonical requirements, rather than observed Resident working time, distance, waits, detours or intentionally inefficient routes. Equivalent output under the same accepted catalog version should earn the same bonus regardless of whether ingredients were already stored or newly produced; snapshot the effective effort terms when a goal is admitted. The value's manual/derived definition, precise XP conversion and rounding remain undecided. [#130](https://github.com/moritzbrantner/my-farm/issues/130), [#133](https://github.com/moritzbrantner/my-farm/issues/133), [#200](https://github.com/moritzbrantner/my-farm/issues/200). Tags: `catalog`, `progression`, `xp`, `balance`. Legacy alias: `my-farm/production/rewards/standard-catalog-effort`.
    - **3.5.3** [agreed; implementation unverified] **C — Derive standard effort, allow catalog overrides.** By default derive a product/recipe's standard production effort deterministically from its declared requirements and ingredient/recipe dependency graph. Allow an explicit, validated catalog override for deliberate gameplay balancing. Record which effective value was derived or overridden, and snapshot that value and catalog identity when a production goal is admitted; subsequent balance edits do not modify previously accepted goal rewards. Actual Resident walking, waiting, route inefficiency, number of goals and UI timing never increase standard effort. The specific graph weights, treatment of alternative recipes, XP conversion rate and rounding remain undecided. See 3.5.2, 3.5.1 and 3.1.2. ([#130](https://github.com/moritzbrantner/my-farm/issues/130); [#133](https://github.com/moritzbrantner/my-farm/issues/133); [#200](https://github.com/moritzbrantner/my-farm/issues/200))

- **Cross-decision references (navigation; no new IDs)**

  - `3.1.1` (automatic goals) must respect `3.1.2` (all-or-nothing reservations) and `3.1.3` (backed future output).

  - `3.3.2` (successful Barn deposit credits production) relies on `3.3.1` (new output, not stored target); `3.3.3` (spendable deposited output) preserves historical credited progress.

  - `3.5.1` (goal-completion XP bonus) is awarded once at `3.3.2`; `3.5.2` fixes the standard catalog effort basis and `3.5.3` approves derivation with explicit overrides.
