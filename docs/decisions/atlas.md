- **How to use this Decision Atlas**
  - This project owns one canonical Markdown source: `docs/decisions/atlas.md`. It is the durable place for **what the product should be**. GitHub issues contain work/acceptance contracts; code and tests contain implementation/evidence; the shared Decision Atlas viewer is read-only.
  - The Atlas has exactly **two semantic leaf-entry kinds: Decision and Question**. Navigation branches only organize entries and are not a third kind. Existing leaves not explicitly marked `[question]` are Decisions.
  - A **Decision** is owner-selected product intent. Agents follow it until a later Decision explicitly supersedes it. A **Question** is a consequential unresolved choice. Write new Question leaves with `[question]`; they are not automatically blockers.
  - Coding agents retrieve the relevant Atlas entries before making consequential product choices. Follow applicable Decisions. If an unanswered Question materially affects the current task, ask the owner **one question at a time**. If a new consequential fork is discovered, append a Question instead of choosing silently.
  - When a Question is answered, keep the Question and append a Decision that says `Answers X.Y`. When a Decision changes, keep it and append a Decision that says `Supersedes X.Y`. Do not add parallel entry categories such as constraint, deferred decision, assumption, or principle; express those meanings in the Decision/Question text and relationships.
  - Every explicit dotted number is a stable entry or navigation-branch ID, for example `3.5.2`. Cross-references refer to these IDs, **not** Markdown's automatic numbering.
  - **Append-only rule:** add the next unused child number under the relevant parent; never renumber, reorder, delete or reuse an existing ID. Concurrent writers must reconcile sibling IDs before merging.
  - Older `my-farm/...` path IDs are preserved as legacy aliases on the imported Decisions. Do not reinterpret or recycle those older identifiers; use dotted IDs for future references.
  - `[agreed; implementation unverified]` is implementation evidence on a Decision, not another Atlas entry kind. It means the owner has selected a design, not that the corresponding gameplay works. Add precise source/test references only after checking them. Existing architectural [ADRs](https://github.com/moritzbrantner/my-farm/tree/main/docs/adr) remain valid and distinct.
  - **Audited implementation checkboxes (2026-10-12 pilot):** A nested `- [x]` means only that the *specific capability named on that line* has concrete linked implementation or independently recorded acceptance evidence; `- [ ]` means that named capability or independent proof remains outstanding. A checked prerequisite never means the broader Decision or parent PRD is complete. No checklist means that Decision has **not yet been audited**, not that its implementation is missing. Do not check inferred results, or mistake code/CI for a publicly verified end-to-end journey. Checklists are evidence annotations, **not additional Decision/Question kinds**, issue states or separate product authority. The current read-only DAQ index does not index these nested evidence annotations; its conservative `implementation unverified` summary remains until complete independent coverage is established.

  - **3.5** Goal-completion XP
    - **3.5.1** [agreed; implementation unverified] **B** — Completing a player-authored finite `Produce N new` goal grants **additional XP** beyond existing farming/production XP, exactly once on the final successful goal-attributed Barn deposit (N/N). Incomplete or cancelled goals earn no completion XP. The XP is awarded by the authoritative Farm progression model and shown in the compact completion notification/history; **selected B:** completion XP scales with genuine goal-attributed production effort. Equivalent work (one 10-Bread goal versus ten 1-Bread goals) should earn approximately the same aggregate bonus, without a flat per-goal jackpot. The effort metric is now **B: standard catalog production difficulty based on canonical product/recipe requirements**, not actual Resident time, travel, waiting or inefficient work. The standard value's manual/derived authoring method and XP conversion rate remain open; no diminishing-repeat policy is approved. [#200](https://github.com/moritzbrantner/my-farm/issues/200), [#133](https://github.com/moritzbrantner/my-farm/issues/133), [#135](https://github.com/moritzbrantner/my-farm/issues/135). Tags: `progression`, `xp`, `reward`. Legacy alias: `my-farm/production/rewards/goal-completion-bonus-xp`.
    - **3.5.2** [agreed; implementation unverified] **B** — Bonus XP uses the product/recipe's **standard catalog-defined production effort** grounded in its canonical requirements, rather than observed Resident working time, distance, waits, detours or intentionally inefficient routes. Equivalent output under the same accepted catalog version should earn the same bonus regardless of whether ingredients were already stored or newly produced; snapshot the effective effort terms when a goal is admitted. The value's manual/derived definition, precise XP conversion and rounding remain undecided. [#130](https://github.com/moritzbrantner/my-farm/issues/130), [#133](https://github.com/moritzbrantner/my-farm/issues/133), [#200](https://github.com/moritzbrantner/my-farm/issues/200). Tags: `catalog`, `progression`, `xp`, `balance`. Legacy alias: `my-farm/production/rewards/standard-catalog-effort`.
    - **3.5.3** [agreed; implementation unverified] **C — Derive standard effort, allow catalog overrides.** By default derive a product/recipe's standard production effort deterministically from its declared requirements and ingredient/recipe dependency graph. Allow an explicit, validated catalog override for deliberate gameplay balancing. Record which effective value was derived or overridden, and snapshot that value and catalog identity when a production goal is admitted; subsequent balance edits do not modify previously accepted goal rewards. Actual Resident walking, waiting, route inefficiency, number of goals and UI timing never increase standard effort. The specific graph weights, treatment of alternative recipes, XP conversion rate and rounding remain undecided. See 3.5.2, 3.5.1 and 3.1.2. ([#130](https://github.com/moritzbrantner/my-farm/issues/130); [#133](https://github.com/moritzbrantner/my-farm/issues/133); [#200](https://github.com/moritzbrantner/my-farm/issues/200))

    - **3.5.4** [agreed; implementation unverified] **B — Canonical recipe sets a product's XP effort.** If a product has multiple valid recipes, the catalog designates **one canonical reference recipe** for deriving its standard production effort. Alternative recipes may be used for actual production but do not change the goal-completion XP for that product. The validated catalog override from 3.5.3 can still replace the derived standard. Preserve the effective standard when admitting the goal. This settles the alternative-recipe choice left open in 3.5.3; see 3.5.2 and 3.5.1. ([catalog #130](https://github.com/moritzbrantner/my-farm/issues/130); [progression #133](https://github.com/moritzbrantner/my-farm/issues/133); [automatic goals #200](https://github.com/moritzbrantner/my-farm/issues/200))

  - `3.4.1` (bounded completed history) records outcomes only after `3.3.2`.
  - `3.5.1` (goal-completion XP bonus) is awarded once at `3.3.2`; `3.5.2` fixes the standard catalog effort basis, `3.5.3` approves derivation with overrides, and `3.5.4` chooses a canonical recipe for multi-recipe products.
